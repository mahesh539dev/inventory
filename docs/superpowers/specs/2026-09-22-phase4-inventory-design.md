# Phase 4 — Inventory — Design

Parent spec: [`2026-09-20-inventory-qr-sales-app-design.md`](2026-09-20-inventory-qr-sales-app-design.md)
(see "Implementation Phases" #4, and source requirements
[`inventory_qr_sales_app_claude_prompt.md`](../../../inventory_qr_sales_app_claude_prompt.md)
sections 13, 25, 40, 47-48).

## Summary

Manual inventory management: add/remove/adjust stock with a required
reason, admin-only, recorded as an immutable transaction history per
product, plus a fixed low-stock threshold other phases (notably Phase 8's
dashboard) can query against. Sale-driven and return-driven inventory
changes are explicitly out of scope — those are Phase 6 and Phase 7.

## What's already in place (Phase 1)

- `inventory_transactions` table (`lib/db/schema.ts`): `id`, `productId`
  (FK, indexed), `type` (enum: `PURCHASE | SALE | RETURN | ADJUSTMENT |
  DAMAGE | OTHER`), `quantity` (signed integer), `referenceId` (nullable
  uuid), `notes`, `createdBy` (FK to users), `createdAt`. No migration
  needed for this phase.
- `products.currentQuantity` with a `CHECK (current_quantity >= 0)`
  constraint already enforced at the DB level (defense in depth).
- The product edit page (`app/(app)/products/[id]/edit/page.tsx`) already
  has a comment explicitly deferring quantity edits to this phase — its
  `updateProduct`/`updateProductSchema` do not touch `currentQuantity`.

## Role Permissions (source spec section 25)

- **ADMIN**: can adjust inventory.
- **USER**: cannot adjust inventory, but can view products (and, by
  extension, inventory history — the spec restricts "adjust," not
  "view").

## New Components

### 1. `lib/repositories/inventory.repo.ts`

- `insertInventoryTransaction(data: NewInventoryTransaction): Promise<InventoryTransactionRow>`
- `listTransactionsByProduct(productId: string, params: { limit: number; offset: number }): Promise<InventoryTransactionRow[]>`
  — ordered newest-first.
- `countTransactionsByProduct(productId: string): Promise<number>`
- `countLowStockProducts(threshold: number): Promise<number>` /
  `listLowStockProducts(threshold: number, params: { limit: number; offset: number }): Promise<ProductRow[]>`
  — `currentQuantity <= threshold AND status = 'ACTIVE'`. Defined now for
  Phase 8 to consume; no dashboard UI is built in this phase.

Only this file touches the `inventoryTransactions` table directly,
matching the existing per-entity repository convention.

### 2. `lib/services/inventory.service.ts`

`adjustInventory(input: { productId: string; quantityDelta: number; type: "PURCHASE" | "ADJUSTMENT" | "DAMAGE" | "OTHER"; notes: string; userId: string }): Promise<ProductRow>`

- Loads the product; throws `ProductNotFoundError` (reusing the existing
  error class from `product.service.ts`) if missing.
- Rejects a `quantityDelta` of `0` (a no-op adjustment isn't a real
  transaction) — validated primarily at the Zod layer, re-checked here as
  a service-level invariant.
- Runs the following atomically inside a single DB transaction (Drizzle's
  `db.transaction()`), taking `SELECT ... FOR UPDATE` on the product row
  first — the same concurrency-safety pattern the parent spec mandates
  for sale completion, applied here because two concurrent adjustments on
  the same product must not both read a stale `currentQuantity`:
  1. Re-read `currentQuantity` under the row lock.
  2. Compute `newQuantity = currentQuantity + quantityDelta`; if
     `newQuantity < 0`, throw `InsufficientInventoryError` (new error
     class) — the DB `CHECK` constraint is the backstop, this is the
     user-facing rejection path.
  3. Update `products.currentQuantity` to `newQuantity`.
  4. Insert the transaction row (`type`, signed `quantity: quantityDelta`,
     `notes`, `createdBy: userId`).
  5. Return the updated product row.

`type` is a required, explicit field the caller supplies (matching the
spec's literal `Reason: New stock` / `Reason: Damaged` examples) rather
than being inferred purely from the sign of the delta — a negative delta
could be `ADJUSTMENT`, `DAMAGE`, or `OTHER`, and a positive one is
typically `PURCHASE` but could be `OTHER` (e.g. a correction found extra
stock). `RETURN` and `SALE` are intentionally excluded from this
function's accepted `type` values — those are system-generated by Phase 6
(sale completion) and Phase 7 (returns), never user-selected here.

### 3. `lib/validation/inventory.schema.ts`

```
adjustInventorySchema = z.object({
  quantityDelta: <signed non-zero integer string, coerced>,
  type: z.enum(["PURCHASE", "ADJUSTMENT", "DAMAGE", "OTHER"]),
  notes: z.string().trim().min(1, "A reason is required"),
})
```

`notes` is required and non-empty here (unlike the optional `notes` on
the product schema) — the source spec says "require a reason for manual
adjustments."

### 4. `lib/actions/inventory.actions.ts`

`adjustInventoryAction(productId: string, prevState: InventoryFormState, formData: FormData): Promise<InventoryFormState>`

- `requireAdmin()` first.
- Parses/validates via `adjustInventorySchema`.
- Calls `adjustInventory`, mapping `InsufficientInventoryError` to a
  field-level form error (not a thrown exception to the error boundary —
  this is an expected, correctable user input state, unlike
  `ProductNotFoundError` which indicates something has gone genuinely
  wrong).
- On success: `revalidatePath('/products/[id]')`,
  `revalidatePath('/products/[id]/history')`, redirect to
  `/products/[id]`.

### 5. Adjust Stock page — `app/(app)/products/[id]/adjust/page.tsx`

`requireAdmin()`-gated page. Shows current quantity as read-only context,
a signed-quantity input, a `type` selector (the four manual-eligible
values), and a required reason textarea — one unified form, not separate
Add/Remove flows, matching the spec's own example layout (`Adjustment:
+5` / `Adjustment: -2` under the same "Inventory Adjustment" heading).

Linked from the product detail page via an admin-only "Adjust Stock"
button, alongside the existing Edit/Archive/Regenerate QR actions.

### 6. History page — `app/(app)/products/[id]/history/page.tsx`

`requireUser()`-gated (any authenticated staff, not admin-only — viewing
is not restricted per the spec). Paginated table of that product's
`inventory_transactions`: type, signed quantity, reason (notes), who
(`createdBy` resolved to a user name), when (`createdAt`, business
timezone). Linked from the product detail page for any authenticated
viewer.

### 7. Low-stock threshold

A single shared constant, e.g. `LOW_STOCK_THRESHOLD = 5` in
`lib/constants.ts` (new small file) — not an env var and not a
per-product column. Rationale: the source spec and parent design spec
never define a per-product reorder point, only "low-stock products" as a
flavor of seed data and "low-stock detection" as a phase-list bullet; the
parent spec's "Out of Scope for V1" list explicitly excludes low-stock
*notifications*, but detection (a query) is listed as this phase's job so
Phase 8's dashboard has something to query. A fixed constant is simplest
and easiest to promote to configurable later without a schema migration.

## Data Flow

```
Admin opens /products/[id]/adjust
        │
        ▼
Submits signed quantity + type + reason
        │
        ▼
adjustInventoryAction → requireAdmin() → adjustInventory (service)
        │
        ▼
DB transaction: SELECT...FOR UPDATE product row
        │
        ├── newQuantity < 0 → InsufficientInventoryError → form error
        │
        └── else → update products.currentQuantity
                  → insert inventory_transactions row
                  → commit
        │
        ▼
Redirect to /products/[id] (updated quantity visible immediately)
```

## Error Handling

- Unknown `productId` → `ProductNotFoundError` (existing class, reused).
- Adjustment would push quantity negative → new
  `InsufficientInventoryError`, surfaced as a field-level form error, not
  a thrown/boundary-level error — this is an expected user-correctable
  case (e.g. admin mistypes `-50` instead of `-5`).
- Zero-delta submission → rejected at the Zod layer with a field error
  before reaching the service.
- Missing/empty reason → rejected at the Zod layer.

## Testing

- **Unit:** `adjustInventorySchema` (rejects zero delta, rejects empty
  reason, accepts valid signed integers); `adjustInventoryAction`
  (admin-gating, rejects non-admin before calling the service, maps
  `InsufficientInventoryError` to a field error).
- **Integration (real dev DB):**
  - `adjustInventory` increases and decreases quantity correctly and
    writes a matching transaction row with the correct signed quantity.
  - `adjustInventory` rejects (throws `InsufficientInventoryError`,
    writes no transaction row, quantity unchanged) when the delta would
    go negative.
  - **Concurrency test**: two simultaneous `adjustInventory` calls against
    a product with exactly enough stock for one of them to succeed —
    assert exactly one succeeds and the other is rejected, and the final
    `currentQuantity` never goes negative (mirrors the parent spec's
    concurrency-safety requirement for sales, applied here since this is
    the first place in the codebase that needs row-level locking).
  - `listTransactionsByProduct` / `countTransactionsByProduct` pagination
    and ordering (newest first).
  - `listLowStockProducts` / `countLowStockProducts` correctly filter by
    threshold and `ACTIVE` status.

## Out of Scope for This Phase

Sale-driven inventory reduction (Phase 6), return-driven inventory
restoration (Phase 7), the dashboard low-stock tile UI (Phase 8),
low-stock notifications (excluded from V1 entirely per the parent spec),
per-product configurable thresholds, CSV-driven bulk inventory changes
(Phase 9 covers CSV import/export generally, not specifically inventory
adjustment).
